# PROJECT ENHANCEMENT: REPLACE PLAYER AVATAR WITH SPIDER-MAN

## 1. ROLE & WORKING MODE

Act as a Senior Three.js Engineer, 3D Character Technical Artist, Multiplayer Game Engineer, and Technical Product Architect.

You are working on an existing production website:

https://danangbridges.netlify.app/

The project is an interactive 3D experience that allows users to explore the bridges and scenery of Da Nang, Vietnam.

Your task is to investigate the existing codebase and create a detailed **Feature Specification (SPEC) and Implementation Plan** for replacing the current human character with a Spider-Man 3D character in two specific transportation modes.

You MUST use the Superpowers workflow to produce the specification and implementation plan.

### Mandatory Superpowers workflow

1. Use the `brainstorming` skill first to understand the feature, investigate the existing implementation, identify constraints, and define the expected experience.
2. Use the `writing-plans` skill to produce a detailed, actionable implementation plan.
3. Follow the actual skill instructions available in the environment. Do not invent unavailable Superpowers commands.
4. Do not begin implementation in this phase. This task is strictly for repository analysis, asset research, specification, and planning.

---

## 2. FEATURE OBJECTIVE

Currently, the characters displayed in the following two modes look like ordinary young Asian male characters:

- Walking mode (Đi dạo).
- Motorcycle mode (Xe máy).

I want to replace these characters with a visually impressive, recognizable Spider-Man 3D character.

The experience should feel like users are exploring Da Nang as Spider-Man rather than controlling an ordinary human avatar.

### Target experience

**Walking mode:**
- Users control Spider-Man walking around the existing 3D environment.
- Spider-Man should have natural idle and walking animations.
- Running animation should also be supported if the current movement system supports running.
- The character should respond naturally to movement and turning.
- The character must remain correctly positioned relative to the ground.
- No floating, sliding, twisting, or unnatural body deformation.

**Motorcycle mode:**
- Spider-Man should be riding the existing motorcycle.
- His body should have a natural motorcycle riding posture.
- Both hands should align with the handlebars.
- Feet and legs should fit naturally around the motorcycle.
- The body should follow the motorcycle's steering, turning, acceleration, deceleration, and movement.
- Avoid clipping between the character's body and the motorcycle.
- The character should look like Spider-Man actually riding the motorcycle, not an ordinary standing character placed on top of a bike.

The final result should be visually coherent in both modes.

---

## 3. STRICT SCOPE

Only replace the existing player character in:

1. Walking mode.
2. Motorcycle mode.

Do NOT change:
- Paragliding mode.
- Car mode.
- Guided sightseeing mode.
- Existing bridges, buildings, terrain, roads, lighting, weather, or environment.
- Existing movement controls.
- Existing camera behavior.
- Existing multiplayer functionality.
- Existing vehicle physics or motorcycle behavior.
- Other features unrelated to this enhancement.

This is a focused character replacement, not a redesign of the application.

## 4. PHASE 1 — INVESTIGATE THE EXISTING PROJECT

Before proposing any implementation architecture, thoroughly review the actual repository.

Do not assume how the current project is implemented.

Inspect the relevant parts of the existing application:

### A. Character rendering
- How is the current human character loaded?
- Is it GLTF/GLB, FBX, or another format?
- Which Three.js loaders are currently used?
- How are character meshes, materials, skeletons, and animations handled?
- How is the character positioned, rotated, and scaled?
- Is the current character shared between walking and motorcycle modes?
- Is there an existing character animation controller?

### B. Walking mode
- How does the walking character move?
- How are idle, walking, and running animations triggered?
- How are character direction and rotation controlled?
- How does the character interact with the ground and environment?
- How is camera tracking implemented?

### C. Motorcycle mode
- How is the motorcycle model loaded and rendered?
- How is the current human character attached to or positioned on the motorcycle?
- Is character positioning calculated dynamically?
- How are steering, turning, and leaning handled?
- Does the motorcycle mode currently use a different character animation system?

### D. Multiplayer synchronization

This is particularly important.

Investigate:
- How local player characters are rendered.
- How remote player characters are rendered.
- How character movement is synchronized.
- How different clients identify and display another player's character.
- Whether character models are loaded independently on each client.
- How mode switching affects the appearance of other players.

The replacement must work consistently for both the local player and remote players.

When another user joins the experience, they should also see the correct Spider-Man character in the appropriate mode.

Review the existing implementation and adapt it. Do not introduce a new multiplayer architecture unnecessarily.

### E. Existing character selection

The application currently exposes character selection options such as Male and Female.

Investigate how these options interact with the existing avatar system.

Determine the most appropriate UX behavior when Spider-Man becomes the character used in walking and motorcycle modes.

Do not blindly remove existing functionality. Check whether the selection is shared with other modes before proposing any UI changes.

### Investigation rule

Use the actual codebase, existing conventions, and current architecture as the source of truth.

Do not propose arbitrary file paths, new systems, or architectural abstractions without first checking whether equivalent functionality already exists.

## 5. PHASE 2 — RESEARCH 3D SPIDER-MAN ASSETS

Find a suitable downloadable Spider-Man 3D model.

Preferred sources:

- Sketchfab: https://sketchfab.com/
- CGTrader: https://www.cgtrader.com/
- Poly Pizza: https://poly.pizza/
- OpenGameArt: https://opengameart.org/
- Other legitimate free 3D asset repositories.

Do not limit the search to Sketchfab.

### Asset selection requirements

Look for a model with the following properties:

1. Recognizable Spider-Man appearance.
2. High-quality character design and textures.
3. Rigged skeletal structure.
4. Suitable for real-time Three.js rendering.
5. Preferably available in GLB or glTF format.
6. Supports or can reasonably support walking animations.
7. Can be adapted to a motorcycle riding pose.
8. Reasonable polygon count and texture size for browser performance.
9. Can be downloaded and stored locally in the project.
10. Has clearly documented licensing and usage permissions.

### Licensing and intellectual property requirements

Do not assume that a downloadable fan-made Spider-Man model automatically has valid permission for public website use.

For every candidate, investigate:

- Original creator.
- Original source URL.
- Download availability.
- Exact license type.
- Commercial and non-commercial restrictions.
- Attribution requirements.
- Whether modifications and animation retargeting are permitted.
- Whether there is evidence of authorization to distribute or license the Spider-Man character itself.

Prioritize an officially authorized asset with clear usage permissions.

Do not use:
- Ripped models from Marvel games.
- Models extracted from copyrighted games or movies.
- Models with unclear ownership or licensing.
- Assets that prohibit the modifications required by this project.
- Paid assets disguised as free downloads.

If no legally suitable Spider-Man model can be established, do not silently select an unauthorized fan model.

Instead, provide two alternatives:

**Option A:** An officially authorized Spider-Man model with appropriate permissions.

**Option B:** An original superhero character with an appealing masked red-and-blue design, but a sufficiently distinct costume, emblem, silhouette, and visual identity that it does not imitate Spider-Man.

Do not treat Option B as an equivalent Spider-Man asset. Clearly explain the difference and let the project owner decide.

Never invent asset specifications or license information.

If a detail cannot be verified, explicitly mark it as unknown.

Recommend the best candidate based on actual technical compatibility, not just visual appearance.

## 6. PHASE 3 — CHARACTER INTEGRATION SPECIFICATION

Once the existing architecture and potential asset have been investigated, define how the new character should integrate into the existing application.

### A. Shared character experience

The Spider-Man character should maintain a consistent appearance across walking and motorcycle modes.

The following should be consistent:
- Character appearance.
- Proportions.
- Materials and textures.
- Scale.
- Visual quality.
- Multiplayer representation.

The character should not suddenly become a different human model when switching modes.

### B. Walking animation

Define the required animation states based on the existing movement system:

- Idle.
- Walking.
- Running, if supported.
- Turning.
- Stopping.

Animations should transition smoothly.

Avoid:
- Sudden animation jumps.
- Sliding feet.
- Incorrect facing direction.
- Floating above the ground.
- Character movement that is disconnected from the actual movement controller.

### C. Motorcycle animation and posture

Define a suitable solution for the motorcycle riding pose.

Investigate whether the selected model already provides appropriate animations.

If not, assess possible approaches:
- Reuse an existing motorcycle riding animation.
- Retarget a compatible animation.
- Use a suitable static riding pose with the existing motorcycle movement system.

Do not assume that a walking character rig can automatically produce a realistic riding pose.

The final approach must preserve the existing motorcycle control and movement behavior.

### D. Multiplayer behavior

The same visual character replacement must work for:
- Local players.
- Remote players.
- Players joining after an existing session has started.
- Players switching between walking and motorcycle modes.
- Players reconnecting, if supported by the current application.

Do not break existing player synchronization.

Avoid unnecessary changes to networking or the application's current data structures.

Review the existing architecture first and reuse its current conventions.

### E. Asset loading and performance

The plan must address:
- Loading the model efficiently.
- Loading assets only when relevant.
- Avoiding redundant downloads.
- Reusing model resources where appropriate.
- Correct handling of independent animated player instances.
- Texture and material optimization.
- Memory cleanup when leaving or switching modes.
- Loading failures and fallback behavior.

The application should remain responsive on desktop browsers.

Consider mobile compatibility where supported by the current application.

Do not introduce heavy dependencies unless there is a demonstrated technical need.

## 7. PHASE 4 — UI/UX SPECIFICATION

Review the existing character selection and player entry interface.

Propose only necessary UI changes.

The objective is to communicate that the user will control Spider-Man without disrupting the current experience.

Potential improvements:
- Display a Spider-Man character preview.
- Show a visual thumbnail instead of relying only on text.
- Show a small character label.
- Keep mode selection consistent with the existing design.
- Ensure the interface remains responsive.

Do not redesign the entire lobby or transportation mode selection interface.

If the character selection interface becomes redundant for these two modes, explain the proposed behavior and its impact on other modes.
