# FEATURE: REAL-TIME WEATHER-DRIVEN 3D ENVIRONMENT

## 1. PROJECT CONTEXT

Existing project:
https://danangbridges.netlify.app/

This is an interactive Three.js 3D experience that allows visitors to explore famous bridges and the surrounding environment of Da Nang, Vietnam.

The project already has:
- Real-time weather information retrieved from a weather API.
- Current temperature and weather conditions.
- Weather selection controls.
- Weather intensity controls.
- Day/night controls.
- Weather effects and storm simulation.
- Existing environmental lighting and atmospheric effects.
- Multiple exploration modes, including walking, car, motorcycle and paragliding.
- Multiplayer/shared exploration functionality.

The current task is to upgrade the project so that the actual 3D environment automatically reflects the real weather and time in Da Nang.

## 2. CORE OBJECTIVE

Transform the existing 3D environment into a living digital representation of Da Nang.

The real-world weather conditions must directly influence the visual atmosphere of the 3D environment.

Examples:

- When Da Nang is sunny, the 3D world should have realistic sunlight, appropriate sky brightness, natural shadows and atmospheric conditions.
- When Da Nang is cloudy, the sky, cloud coverage, sunlight and ambient lighting should change accordingly.
- When Da Nang is raining, realistic rain particles, wet surfaces, road reflections, water ripples and appropriate atmospheric effects should appear.
- When Da Nang experiences heavy rain, environmental effects should become more intense.
- When Da Nang is foggy, distant objects and the city skyline should become less visible.
- When wind speed increases, vegetation, flags, rain particles and appropriate environmental elements should respond to wind.
- When local time changes from day to sunset and night, the entire environment should transition accordingly.

**The goal is not simply to display weather information. The actual 3D world must visually behave according to the real-world conditions.**

## 3. PHASE 1 — REVIEW EXISTING ARCHITECTURE

Before modifying code, thoroughly inspect the existing project.

Identify:

1. Existing weather API integration.
2. Current weather data structure and state management.
3. Existing weather code interpretation.
4. Existing weather simulation implementation.
5. Current Three.js scene architecture.
6. Sky, clouds, sunlight, ambient lighting and fog implementations.
7. Rain, wind, particle and water effects.
8. Road, bridge and environmental materials.
9. Existing day/night transition system.
10. Existing multiplayer synchronization mechanism.
11. Performance and graphics quality management.

Determine exactly which existing components can be reused.

Do not assume that the existing system uses a particular architecture, library or state management pattern.

Do not create duplicate weather API integrations.

**IMPORTANT: Reuse the same weather data source and state already used by the weather information interface.**

All environmental effects must be driven by the same current weather snapshot shown to visitors.

## 4. PHASE 2 — BUILD A REAL-TIME ENVIRONMENT MAPPING SYSTEM

Create a system that translates actual weather information into 3D environmental parameters.

Use the fields already available from the current weather API.

If some important fields are missing, extend the existing API request only when necessary.

### A. Weather condition mapping

Support these weather states:

**Clear / Sunny**
- Realistic blue sky.
- Appropriate sunlight intensity.
- Natural sunlight direction.
- Realistic shadows.
- Minimal atmospheric haze.
- Natural water reflections.

**Partly Cloudy**
- Dynamic cloud coverage.
- Variable sunlight intensity.
- Natural lighting variation.
- Appropriate sky appearance.

**Overcast / Cloudy**
- Higher cloud coverage.
- Reduced direct sunlight.
- Softer shadows.
- Lower environmental brightness.
- More realistic overcast atmosphere.

**Drizzle / Light Rain**
- Fine rain particles.
- Subtle wet surfaces.
- Small water ripples.
- Slightly darker environment.
- Appropriate cloud and lighting conditions.

**Rain**
- Clearly visible rain particles.
- Rain intensity proportional to actual precipitation.
- Wet roads and bridge surfaces.
- Realistic reflections on wet surfaces.
- Water ripples and rain interactions with the river.
- Appropriate atmospheric haze.

**Heavy Rain**
- Increased rain density and particle speed.
- Stronger surface wetness and reflections.
- More pronounced atmospheric effects.
- Reduced visibility when supported by actual weather conditions.

**Fog**
- Realistic atmospheric fog.
- Reduced distant visibility.
- Gradual depth-based fog density.
- Preserve visibility of important landmarks and bridges.

**Thunderstorm**
- Use actual thunderstorm conditions from the weather API.
- Stronger wind and rain effects when supported by the data.
- Realistic atmospheric lighting.
- Optional subtle lightning effects.
- Do not trigger dramatic lightning randomly when the actual weather data does not indicate a thunderstorm.

### B. Cloud coverage

Use actual cloud coverage information when available.

Map cloud coverage to:
- Sky appearance.
- Cloud density.
- Direct sunlight intensity.
- Ambient lighting.
- Shadow softness.

Avoid treating every cloudy condition as completely overcast.

Cloud coverage should influence the environment gradually.

### C. Precipitation and rain

Use actual precipitation measurements to control:
- Rain particle density.
- Rain particle velocity.
- Rain direction.
- Surface wetness.
- Road reflections.
- Bridge reflections.
- Water ripples.

Rain intensity must be proportional to the measured precipitation.

Do not display heavy rain when actual precipitation is zero or negligible.

When rainfall stops:
- Stop new rain particles.
- Gradually reduce wet-weather effects.
- Allow surfaces to become less reflective over time.
- Avoid abruptly returning the entire environment to a dry state.

### D. Wind behavior

Use actual wind speed and wind direction.

Apply wind influence to appropriate objects:
- Trees and vegetation.
- Flags and decorative elements.
- Rain trajectories.
- River surface movement and waves.
- Other existing environmental objects that support wind animation.

Wind movement should be subtle at low speeds and progressively stronger at higher speeds.

Use physically plausible limits to prevent exaggerated movement.

### E. Humidity and atmospheric visibility

Use available humidity and visibility information to adjust atmospheric appearance.

Requirements:
- Higher humidity may contribute to subtle atmospheric haze.
- Actual fog conditions should produce more noticeable visibility reduction.
- Do not interpret high humidity alone as dense fog.
- Keep important landmarks recognizable.

### F. Temperature

Use actual temperature as part of the environmental state.

Temperature may influence subtle atmospheric presentation if the existing rendering architecture supports it.

Do not invent unrealistic visual effects simply because the temperature changes.

## 5. PHASE 3 — REAL-TIME LOCAL TIME SYNCHRONIZATION

The environment must also follow actual local time in Da Nang.

Use the Asia/Ho_Chi_Minh timezone.

Automatically synchronize:
- Sun position.
- Sunlight direction.
- Sunlight intensity.
- Sky color.
- Ambient lighting.
- Shadow appearance.
- Sunset and sunrise transitions.
- Nighttime atmosphere.

Expected visual transitions:

**Morning**
- Gradual sunrise atmosphere.
- Warm sunlight.
- Natural morning sky.

**Midday**
- Stronger sunlight.
- Natural daylight.
- Appropriate shadow direction.

**Afternoon**
- Gradually changing sunlight.
- Warmer atmospheric lighting.

**Sunset**
- Orange and warm atmospheric colors.
- Gradual reduction in sunlight intensity.
- Beautiful reflections across the Han River.

**Night**
- Darker sky.
- Reduced natural sunlight.
- Existing bridge illumination and city lights become visually prominent.
- Realistic reflections from bridge lights and surrounding buildings.

Important:
- Do not use fixed arbitrary time ranges if the existing architecture can calculate solar position more accurately.
- The environment must transition smoothly.
- Do not abruptly switch between day and night.
- Do not conflict with existing bridge lighting schedules or user-controlled lighting settings.

## 6. PHASE 4 — LIVE MODE AND MANUAL SIMULATION MODE

This requirement is extremely important.

The project already has manual weather and day/night simulation controls.

Preserve all existing simulation functionality.

Introduce two clearly separated environment modes:

### MODE A: LIVE WEATHER

In this mode:
- Real weather API data controls the 3D environment.
- Local time controls the day/night atmosphere.
- Weather updates are applied automatically.
- Users cannot accidentally override live weather through simulation controls without explicitly switching modes.

Display an easy-to-understand Live indicator.

Example:
LIVE WEATHER · DA NANG

### MODE B: MANUAL SIMULATION

In this mode:
- Preserve existing weather selection.
- Preserve weather intensity.
- Preserve existing storm scenarios.
- Preserve day/night controls.
- Preserve existing weather effects and bridge interactions.

Manual settings must remain independent of the real weather API.

When switching from Manual Simulation back to Live Weather:
- Fetch or use the latest available real weather data.
- Recalculate environmental parameters.
- Smoothly transition the 3D scene to the actual conditions.

Do not allow an automatic API refresh to overwrite manually selected weather.

Live Weather should be the default mode when actual weather data is available, while retaining all existing manual simulation capabilities.

## 7. PHASE 5 — ENVIRONMENTAL REALISM

Prioritize visual realism.

The following elements deserve special attention:

**Han River**
- Realistic reflections under different lighting conditions.
- Rain ripple effects.
- Natural water surface response to wind.
- Appropriate appearance during night and sunset.

**Bridges**
- Wet surface appearance during rain.
- Natural reflections.
- Appropriate lighting under different weather conditions.
- Preserve existing bridge structures and details.

**Roads**
- Wet road materials during precipitation.
- Realistic specular reflections.
- Avoid excessive mirror-like reflections.

**Vegetation**
- Natural wind response.
- Appropriate lighting under different weather conditions.

**City atmosphere**
- Realistic sky and atmospheric depth.
- Correct lighting under clear, cloudy and rainy conditions.
- Natural visibility changes.

Do not introduce flooding, rising river levels, damaged infrastructure or other major physical events based solely on rain measurements.

## 8. PHASE 6 — MULTIPLAYER CONSISTENCY

The project includes a shared exploration experience.

Investigate the current multiplayer architecture.

All connected visitors should experience consistent real-world environmental conditions.

Requirements:
- Avoid different weather conditions between visitors exploring the same shared environment.
- Use the same weather source and timestamp.
- Reuse existing synchronization infrastructure where available.
- Ensure manual simulation and live weather synchronization do not conflict.
- Avoid introducing a new backend or networking infrastructure unless the existing architecture genuinely requires it.

Weather synchronization should not interfere with player movement, vehicle controls or camera synchronization.

## 9. PHASE 7 — PERFORMANCE OPTIMIZATION

The project must remain smooth on normal desktop computers and reasonably capable mobile devices.

Requirements:

- Reuse existing Three.js render loops.
- Do not introduce duplicate animation loops.
- Reuse particle geometries and materials.
- Use object pooling where appropriate.
- Avoid creating and destroying large numbers of objects every frame.
- Use efficient material updates.
- Use smooth interpolation between environmental states.
- Respect existing graphics quality settings.
- Provide adaptive weather effects for lower-end devices.
- Dispose of resources correctly when they are no longer needed.

Do not sacrifice the overall visual quality unnecessarily.

## 10. WEATHER REFRESH AND ERROR HANDLING

The weather API should not be called continuously.

Requirements:
- Reuse the existing weather refresh mechanism.
- Refresh actual weather data periodically, approximately every 10–15 minutes, subject to the existing API configuration and provider limits.
- Update the 3D environment smoothly between API refreshes.
- Validate missing, invalid and out-of-range values.
- Display the timestamp of the weather data used.
- Handle API failures gracefully.
- Keep the last known valid weather state when connectivity is temporarily unavailable.
- Do not invent weather information.
- Reconnect and update the environment when valid data becomes available again.

The visual environment should never change abruptly simply because a new API response arrives.

## 11. PHASE 8 — TESTING

Test at least the following scenarios:

1. Clear sky during daytime.
2. Partly cloudy conditions.
3. Fully overcast conditions.
4. Light rain.
5. Heavy rain.
6. Fog.
7. Strong wind.
8. Thunderstorm conditions.
9. Sunset transition.
10. Nighttime.
11. Weather changes between two API updates.
12. API connection failure.
13. Switching from Live Weather to Manual Simulation.
14. Switching back to Live Weather.
15. Existing storm simulation.
16. All exploration modes.
17. Multiplayer environment consistency.
18. Low graphics quality settings.

Use controlled mock weather states for testing where actual weather conditions are unavailable.

Ensure that mock testing never overwrites or contaminates production weather data.

## 12. ACCEPTANCE CRITERIA

The feature is complete only when:

- Actual weather data controls the 3D environment.
- Local time controls the environmental lighting and day/night transitions.
- Rain intensity reflects actual precipitation.
- Cloud coverage visibly affects the sky and lighting.
- Wind affects appropriate environmental objects.
- Fog and visibility behave realistically.
- Environmental transitions are smooth.
- Live and Manual Simulation modes operate independently.
- Existing manual weather controls continue working.
- All exploration modes remain functional.
- Multiplayer visitors see consistent environmental conditions.
- No major performance regression is introduced.
- Existing website functionality remains intact.

## 13. IMPLEMENTATION WORKFLOW

Use the Superpowers workflow.

First:
1. Inspect the project.
2. Understand the existing implementation.
3. Write a clear technical specification.
4. Identify affected modules and dependencies.
5. Create an implementation plan with independent tasks.
6. Define testing scenarios and acceptance criteria.

Then implement in logical stages.

Recommended implementation stages:

- Stage 1: Weather data normalization and environmental state.
- Stage 2: Real-time weather-to-3D mapping.
- Stage 3: Dynamic sky, clouds and lighting.
- Stage 4: Rain, wind, fog and wet surface effects.
- Stage 5: Real-time sun and local time synchronization.
- Stage 6: Live/Manual mode integration.
- Stage 7: Multiplayer consistency.
- Stage 8: Performance optimization and regression testing.

After each stage:
- Run relevant tests.
- Verify existing features.
- Document completed work.
- Record any remaining limitations.

Do not stop after writing the specification or implementation plan. Proceed with implementation unless a genuinely blocking architectural issue or destructive decision requires my input.

## 14. FINAL EXPECTATION

The final experience should make visitors feel that they are exploring Da Nang in real time, not looking at a static 3D model.

A visitor opening the website on a rainy evening should experience a rainy nighttime version of Da Nang.

A visitor opening it on a clear sunny morning should experience a bright, naturally illuminated city.

The world should continuously reflect the actual weather and local time.

**Visual realism, environmental consistency, performance and preservation of existing functionality are the highest priorities.**

Do not redesign unrelated parts of the website. Focus on making the existing 3D world alive and responsive to real-world environmental conditions.
