## 3. CORE FEATURE: PROXIMITY-BASED CHAT

The fundamental rule:

**A participant can only exchange chat messages with other participants who are physically within the configured proximity radius in the shared 3D world.**

Examples:

- Player A and Player B are close to each other: They can exchange messages.
- Player C is far away: Player C cannot receive their conversation.
- Player C approaches A and B: Player C becomes eligible to participate in the local proximity chat.
- Player A moves away: Player A stops receiving new messages from participants outside the configured range.

This must be a genuine proximity-based communication system, not simply a UI that displays nearby player names while broadcasting messages globally.

### 3.1 Proximity Detection

Implement a reliable distance-based detection mechanism.

Requirements:

- Determine the actual position representation used by the existing multiplayer system.
- Calculate the distance between participants using their synchronized world positions.
- Use a configurable proximity radius.
- Choose a sensible default based on the actual scale of the 3D environment and the speed of each movement mode.
- Do not blindly assume that one Three.js world unit equals one real-world meter.
- Support all existing exploration modes.
- Detect when participants enter or leave proximity range.
- Avoid excessive distance calculations or unnecessary network traffic.
- Handle player movement and vehicle switching correctly.

The proximity system should remain lightweight because the experience supports a maximum of 5 simultaneous participants.

### 3.2 Local Message Delivery

Implement real-time text message delivery.

Expected behavior:

1. Player A sends a message.
2. The system identifies participants who are currently within A's proximity radius.
3. Only eligible participants receive the message.
4. Player A also sees their own message.
5. Participants outside the radius must not receive the message.
6. When a participant moves out of range, they must stop receiving new messages from that local conversation.
7. When a participant enters the radius, they become eligible to receive subsequent messages.

If multiple participants are within the same proximity area, they should be able to participate in the same local conversation.

Do not implement global chat.

Do not implement voice chat in this phase. Text-based communication is the only required feature.

### 3.3 Real-time Networking

Inspect the current networking architecture before choosing an implementation.

Reuse the existing real-time communication mechanism whenever possible.

If additional networking functionality is necessary, select the smallest solution compatible with the current backend and deployment environment.

Important requirements:

- Avoid unnecessary polling.
- Avoid broadcasting every chat message to all connected participants.
- Avoid duplicating existing position synchronization.
- Ensure multiple clients receive messages with minimal latency.
- Handle network interruptions gracefully.
- Handle stale participant positions.
- Remove disconnected participants from proximity calculations.
- Ensure messages are correctly associated with their sender.

**Important security requirement:**

Proximity authorization should not rely exclusively on a client-side distance check.

Validate message recipients using the most authoritative position data available in the existing architecture. A modified client must not be able to send messages to participants outside the allowed range.

Do not expose backend credentials or privileged secrets in browser code.

## 4. CHAT USER INTERFACE AND EXPERIENCE

The chat interface must feel like a natural part of the 3D exploration experience.

It must not cover too much of the screen or distract users from exploring Da Nang.

### 4.1 Chat Interface

Create a compact, modern floating chat interface.

Suggested elements:

- A small chat icon/button.
- An unread message indicator.
- A nearby participants indicator.
- A collapsible chat panel.
- Message history.
- Sender display name.
- Message timestamp.
- Text input.
- Send button.

The interface should be visually consistent with the existing website.

Avoid introducing an unrelated design language.

### 4.2 Chat States

Support the following states:

**State A — No nearby participants**

Display a subtle message such as:

"No one nearby to chat with."

The chat interface should still be accessible, but sending messages should be disabled or clearly indicate that nobody is within range.

**State B — One nearby participant**

Display the nearby participant's name.

Example:

"You are near Minh."

Both participants can exchange messages.

**State C — Multiple nearby participants**

Display the number of nearby participants.

Example:

"3 people nearby."

Allow everyone currently within range to participate in the local proximity conversation.

**State D — Participant leaves the proximity range**

Update the nearby participant indicator.

Stop delivering new messages from participants who are no longer within range.

**State E — Network disconnected**

Display a subtle connection warning.

Do not silently pretend that messages have been delivered.

### 4.3 Message Presentation

Messages should be easy to distinguish:

- My messages should appear on the right.
- Other participants' messages should appear on the left.
- Show the sender's name.
- Show a subtle timestamp.
- Automatically scroll to the latest message when appropriate.
- Preserve readability without consuming too much screen space.

Support Enter to send and Shift + Enter for a new line.

Set a reasonable maximum message length.

Provide basic sending feedback so users know whether a message was sent successfully.

### 4.4 Immersive 3D Interaction

Where technically practical, implement a small temporary speech bubble above the sender's 3D character.

For example:

- A participant sends "Hello!"
- Other nearby participants can see a short-lived speech bubble above that participant.
- The bubble disappears automatically after a reasonable duration.

This should be a lightweight visual enhancement, not a mandatory dependency for the chat system.

Do not add expensive 3D geometry or animations that negatively affect rendering performance.

## 6. EDGE CASES AND RELIABILITY

Think carefully about these scenarios:

1. Two participants approach each other simultaneously.
2. Two participants are exactly at the proximity boundary.
3. A participant rapidly moves in and out of range.
4. A participant disconnects while chatting.
5. A participant reconnects.
6. One participant changes from walking to motorcycle.
7. All five participant slots are occupied.
8. A participant enters an area where several other participants are already chatting.
9. The network temporarily disconnects.
10. Two participants send messages at almost exactly the same time.
11. A participant attempts to send an empty message.
12. A participant sends extremely long messages.
13. A malicious client attempts to spoof another participant's identity.
14. A participant attempts to send messages to someone outside the proximity radius.

The system must recover gracefully without crashing or disrupting the 3D experience.
